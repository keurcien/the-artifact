# apps/api

Hono on Node 26, Drizzle ORM over `postgres`, S3 via `@aws-sdk/client-s3`, MCP via `@modelcontextprotocol/server`, thumbnails via `playwright-core` driving headless Chromium. Runs with `tsx watch` in dev, `tsc` → `dist/` in production.

## Where things are

| File | Responsibility |
| --- | --- |
| `src/index.ts` | Boot of the long-running server: one process, or with `WEB_CONCURRENCY` above 1 a `node:cluster` primary (`src/primary.ts`) and its workers. Vercel runs `api/index.js` instead and never forks |
| `src/startup.ts`, `src/server.ts`, `src/primary.ts`, `src/workers.ts` | Once per server before serving: migrations (`MIGRATE_ON_START`), opening the server secrets (`checkServerSecrets`), the bucket check and, on a self-hosted install without accounts, the setup code (`startup.ts`). One serving process (`server.ts`): the HTTP server, graceful shutdown on `SIGTERM`, and in the background process only the storage sweep, the thumbnail queue, sending webhooks and resuming exports left behind. The primary (`primary.ts`) restarts crashed workers with backoff, forwards thumbnails to worker 1 and gathers `/metrics` from every worker. Sizing and IPC messages (`workers.ts`). Anything else that must run once per server (a timer, a queue) goes where `scheduleSweeps` is called in `server.ts`; in-memory state is per worker |
| `src/app.ts` | Mounts every router; `GET /api/config` and `GET /api/me` |
| `src/env.ts` | Environment variables. Add new settings here and read them from `env` |
| `src/db/schema.ts` | Tables. `src/db/index.ts` exports `db`, `schema` and the `Tx` type |
| `src/artifacts.ts` | Pages and versions: access rules (`accessLevel`, `canView`, `canEdit`, `canDelete`), publish, updating some files of the current version (`updateFiles`, `updateUpload`), restore, delete, listing (newest first, paged by an `(updated_at, id)` cursor) |
| `src/content.ts` | Serves a version as a document tree at `/api/artifacts/<slug>/v/<n>/…`, as a zip at `/api/artifacts/<slug>/download` and as a PDF at `/api/artifacts/<slug>/pdf`, link tokens for sandboxed frames and agents' download links; with `CONTENT_ORIGIN`, `contentHost` is all that origin answers (`app.ts` hands it every request on that host) and the app's host redirects page files there |
| `src/cache.ts` | In-process caches (`Lru`, `memo`), one per process: a version's files by version id (`artifacts.ts`), `/api/config`'s account and SSO lookups. Only for immutable rows looked up by a key the request just read fresh (the page row and version row always are), or answers a few seconds old may give |
| `src/frame-helper.ts` | The comment helper added to a page's HTML under `/v/<n>/[~token/]~comments/`, for picking elements and locating pins over postMessage; its trust model is in its header and `docs/security.md` |

| `src/diff.ts`, `src/compare.ts` | Comparing two versions: line diffs (Myers, no dependency) and the changed files with their diffs, capped per file and per comparison (`GET /api/artifacts/<slug>/compare`, `diff_versions`) |
| `src/exports.ts`, `src/routes/exports.ts` | Data exports of an account or, for owners, an organization: a zip built in leased steps of at most 20 s into a multipart upload under `exports/<id>/`, so it fits a serverless function. The long-running server builds in the process asked and resumes left-behind ones in the background process; elsewhere `GET /api/exports` runs a step each time the settings page polls, and `/api/cron/sweep` a few more. Downloads need the requester's session and a signed link, for 24 hours; the storage sweep deletes them after |
| `src/files.ts` | Multi-file page validation and size limits |
| `src/prepare.ts` | Checks, decodes and hashes inline publishes of 256 KB or more on a pool of up to four worker threads, so they don't hold up the event loop, and pulls the text for search out of large pages (`extractText`); `src/files.ts` is the worker's entry, so it imports only Node's own modules. Falls back to the main thread if workers can't start |
| `src/storage.ts`, `src/gc.ts` | Content-addressed blobs in S3 and the sweep that deletes unreferenced ones; `addPruner` jobs run before each sweep |
| `src/thumbnails.ts` | Gallery screenshots of untrusted HTML with no network of its own; `inPage` opens a page under those rules for every render |

| `src/renders.ts` | Renders someone waits for (inspections, PDFs): their slots, apart from the thumbnail queue's, and in a cluster the IPC to the worker with Chromium (`render`, `renderHere`, `renderElsewhere`) |
| `src/previews.ts` | Link preview (Open Graph) tags in the HTML shell of `/a/<slug>`, for link-shared pages only; mounted by `src/web.ts` and by `api/index.js` on Vercel. `SHELL_HEADERS` keeps the app itself out of other sites' frames and sets the shell's CSP |
| `src/embeds.ts` | Embeds: `/e/<slug>` (a link-shared page without the app, framable by other sites, or a sign-in card) and `GET /api/oembed` |

| `src/tags.ts`, `src/routes/tags.ts` | Tags on pages: rules (`checkTag`), changing them (editors), the workspace's tags for the gallery. Seen by everyone who can open the page |
| `src/search.ts` | Search inside pages: the words of each page's current version as a stripped `tsvector` ('simple') in `artifact_search`, matched by listing's `q` alongside the title. Written in the publish transaction for short text, otherwise after the commit (`indexLater`: queued on the long-running server, awaited elsewhere); `staleIds`/`indexStale` catch up from the storage sweep, `/api/cron/sweep` and `search:backfill`. Anything that makes a version current calls `indexLater` (or writes the words itself) |
| `src/mcp-app.ts` | The MCP Apps viewer: `ui://the-artifact/viewer`, one HTML document speaking the extension's JSON-RPC over postMessage, which the page-publishing tools name in `_meta.ui.resourceUri`; and `artifact://<id>/view`, the page's current version under a content link signed for the agent's person, which the viewer frames. `EMBED_FRAME_ANCESTORS` must stay unset for hosts to frame it |

| `src/comments.ts`, `src/routes/comments.ts` | Comments on a page: one level of threads, anchors to an element (`checkAnchor`, untrusted input), moderation by editors, emails throttled by the `comment-email` limit, unread counts from `comment_reads`. Signed-in people who can open the page only |
| `src/views.ts` | Page views: a count per version (`artifact_view_counts`) and who opened a page (`artifact_views`, identified visits only, deleted after 90 days by the storage sweep and `/api/cron/sweep`). Recorded by `serveVersion` for browser navigations to the entry, with repeats in 30 minutes dropped in memory first. The long-running server (`batchViewCounts` in `server.ts`) batches counts in memory and flushes every 5 s and on SIGTERM; elsewhere (Vercel) each view is written directly. Integration tests batch too and call `flushViews` before reading counts |
| `src/webhooks.ts`, `src/routes/webhooks.ts`, `src/network.ts` | Webhooks per workspace (an organization's owners and admins, or the owner of a personal workspace): events from publish, `addComment` and `recordView` (`emitWebhookEvent`, never throws), queued in `webhook_deliveries`. ## Rules that aren't obvious from one file

- **Access.** Owners and invited editors edit; invited viewers view; organization admins and owners edit every page in their organization; general access (`private` shown as "Restricted", `organization`, `link`) opens a page wider. Older versions and history are editor-only. Owning an organization's page counts only while the owner is a member there and not blocked, so nothing may trust `ownerId` alone (`canDelete`, `ownedPages`). Agents and access tokens carry their workspace on the `Viewer` (`workspace`): ownership and organization roles count only for pages in it, shares and links anywhere (`inScope`). Go through `accessLevel`/`canView`/`canEdit`/`canDelete`; don't re-implement checks in routes.
- **Blobs are shared and immutable.** Content lives under `blobs/<sha256>`; rows only hold hashes. Only the API writes there: direct uploads land under `uploads/<id>/` and are hashed before they become blobs. Anything that uploads blobs and then writes rows that reference them must call `holdStorageLock(tx)` inside the same transaction first, or the sweep can delete a blob between upload and commit.
- **Version numbers.** Publish and restore lock the page row (`for update`) before picking the next number. Restore never rewrites history; it publishes the old content as a new version.
- **Tokens are stored hashed** (`hashToken`): sessions, pending sign-ins, email links, invitations, OAuth codes and tokens, access tokens, SCIM tokens, recovery codes, WebAuthn challenges. Links work once; delete the row as it is used.
- **Every first factor ends in `continueSignIn`** (`src/auth/twofactor.ts`), never `startSession`; it also turns away people who must use single sign-on (SSO itself passes the method `'sso'`): an account with a passkey or an authenticator app gets a pending sign-in, and the session starts after the second factor. Only new accounts and a passkey on its own call `startSession` directly. Web-session users carry `blockedOrgs` (organizations that require a second factor they lack); pass the user, not just its id, to `accessLevel`, `belongsTo` and `folderFor` so those organizations stay closed in the app.
- **Writes under `/api` come from the web app.** `sameOriginWrites` (`src/auth/origin.ts`) refuses POST, PUT, PATCH and DELETE without `Sec-Fetch-Site: same-origin` (or an `Origin` of `APP_URL`) and bodies that aren't JSON; bearer requests are exempt. A route other sites must post to (like the SAML ACS) goes in its `CROSS_SITE_PATHS`; anything for clients with their own credentials belongs outside `/api`. Integration tests send `Origin` through `call`.
- **Email links must survive mail scanners.** Opening a sign-in link only shows a confirmation page; the POST on Continue uses it up.
- **New accounts.** Creating accounts and changing admins take `lockAdmins(tx)`. So does deleting an account (`deleteAccount` in `routes/settings.ts`), which also locks the owner rows of the organizations it owns, as the members routes do, and checks the last owner and last admin again under those locks. Insert new users with `...(await newAccountFields(tx, setupCode))`: on a self-hosted install the first account becomes admin and goes through onboarding, and later ones start onboarded in their personal workspace. The first one needs the setup code, or `newAccountFields` throws `SetupCodeError`; a way in that can't ask for the code (Google, single sign-on) turns it into `NeedsSetupError`.
- **Untrusted HTML.** Page content is served with `contentCsp()` (sandbox, opaque origin, framing as `EMBED_FRAME_ANCESTORS` allows) on every file, never with the app's cookies. With `CONTENT_ORIGIN` the content host reads and sets no cookie and serves nothing but page files; anything new that serves untrusted content goes there too, and nothing of the app does. Thumbnails and inspections intercept every request; see the header comment in `src/thumbnails.ts` before touching it, and open pages only through its `inPage`.
- **Limits.** New endpoints that send email or create accounts, clients or content go through `limitRequest` (or `hit`) from `src/limits.ts`, with a limit added to its list and to `docs/configuration.md`. Limits on wrong guesses count the attempt with `hit` before checking it, then `clearHits` or `refund` when it was right; checking first lets attempts sent at once all through. Anything that adds a version calls `checkQuota` inside its transaction.
- Shared helpers: `isEmail` (and `isAccountEmail` for finding existing accounts only) and `UUID_RE` in `src/validation.ts`, `likeTerm` in `src/artifacts.ts` for escaped `ILIKE` searches, `checkTitle` for page names.

## Migrations

1. Edit `src/db/schema.ts`.
2. `pnpm db:generate` (from the repo root) writes `drizzle/NNNN_*.sql` and `drizzle/meta/*`. Rename the SQL file to say what it does if the generated name is random, and update the `tag` in `drizzle/meta/_journal.json` to match.
3. Commit the SQL, the snapshot and the journal together. Never edit a migration that has shipped; add a new one.
4. `pnpm db:migrate` locally. Tests migrate `artifact_test` themselves.

## Tests

- `test/unit/` — pure functions, no services.
- `test/integration/` — calls `app.request()` in-process against `artifact_test` and the `artifact-test` bucket. Every table is truncated before each test and files run serially.
- `test/load/seed.ts` (`pnpm --filter @the-artifact/api load:seed`) seeds a test or staging server for the k6 scripts in `load/`; it refuses other databases.
- Use the helpers in `test/integration/helpers.ts` (`createUser`, `createOrg`, `createPage`, `connectAgent`, `callTool`, `call`) rather than building requests by hand.
- `src/mail.ts` is replaced by a mock in `test/integration/setup.ts` that only has the send functions. Keep non-mail code out of `mail.ts`, and add any new send function to that mock (`src/ee/mail.ts` has a mock of its own).
- `vitest.config.ts` pins `SELF_HOSTED=false` and SMTP on. Tests that need other modes change the `env` object and restore it in `afterEach` (see `admin.test.ts`, `no-email.test.ts`).
- `pnpm --filter @the-artifact/api lint` type-checks `src` and `test` together.
